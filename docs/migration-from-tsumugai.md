# migration-from-tsumugai.md

前身プロジェクト`tsumugai`から`voice-to-tyrano`への知識移行の記録。

`tsumugai`は失敗作ではない。問題設定の変化によって役割を終えたプロジェクトであり、その設計知識の多くは本リポジトリに引き継がれている。

## tsumugaiが解決しようとしていた問題

`tsumugai`（Rust製、約7,300行）は、Markdownで書いたノベルゲームシナリオを「実行前に意味を確定し、検証し、再利用できるようにする」静的検査CLIだった。従来のノベルゲーム制作が抱える次の問題に対抗しようとしていた。

- 分岐が増えると全体を把握・追跡できなくなる
- 到達不能ルートが埋もれる
- 実行（テストプレイ）しないと誤りが分からない
- シナリオが特定エンジンにロックインされブラックボックス化する

そのために、独自シナリオ形式（Markdownベースの記法、SPEC.md約29KB）と、check / trace / routes / fmt / compile の5コマンドを持つ独自の検証・実行基盤を作っていた。

## なぜ方針を変えたか

- **AIによる変換を使えば、既存のティラノスクリプトをそのまま利用できる**と判断した。作者が書きやすい形式（今回は音声の語り）とエンジンが実行できる形式の間を、独自DSLと独自パーサではなくAIが橋渡しできる
- 独自エンジン・独自記法の保守は、目的（作者がシナリオを途切れず書けること）に対して過剰だった。記法仕様の維持、パーサ・検査器・出力系の保守、外部要求記法との互換調整（ADR 0001でv2記法を不採用にした経緯）など、目的と関係の薄い作業が大きかった
- ティラノスクリプトは実績あるランタイム・エコシステム（ティラノビルダー、公式リファレンス、既存素材規約）を持ち、再発明する理由がない

## voice-to-tyranoへ移した設計知識

| tsumugaiでの知識 | 移行先 |
| --- | --- |
| 推測で埋めない方針（fmtは「確信が持てない箇所は変換せず、判断をユーザーに返す」）| SKILL.mdの変換原則・TODOコメント方式 |
| 診断は学習教材（どこ・なぜ・どう直すかを全件報告、最初のエラーで止まらない）| SKILL.mdの検査・完了報告の設計 |
| パースはエラーで中断しない（解釈できた範囲と全診断を両方返す）| 「重大な曖昧さがあっても変換可能な部分を破棄しない」原則 |
| ラベル重複・存在しない遷移先・暗黙フォールスルー・到達不能セクション・循環の検査観点（check/routes）| SKILL.mdの最低限の検査、tests/README.mdの構造検査候補 |
| 静的検査と経路（到達可能性）検査の責務分離 | tests/README.mdの検査分類 |
| CUIで検証できること・CIで保証したいこと（fmt/lint/test+スモーク、1ルール1fixture、ゴールデンテスト）| tests/README.mdのテスト観点・回帰確認の論点 |
| 作者の原稿と生成物の区別（原稿が正、生成物は派生）| docs/design.mdの正本の扱い |
| 独自記法で発生した曖昧さの実例（コロンによるセリフ誤判定、重複アンカー、意図しないフォールスルー、外部要求記法との非互換）| 独自DSLを作らない判断の根拠（本文書）、音声解釈の注意点 |

## 移さなかったコード

実装コードは一切移植しなかった。

- パーサ（parse.rs 約900行）: 独自記法を廃止したため不要。自然言語の解釈はSkill（LLM）が行う
- 検査器（check.rs / routes.rs 約1,150行）: 検査「観点」のみをtests/README.mdへ移した。初期版の検査はSkill自身の確認で足り、コードによる静的検査は必要性が確認できてから再実装する
- 整形器・コンパイラ・トレーサ（fmt.rs / compile.rs / trace.rs 約1,500行）: 独自形式と独自出力（StoryBundle）が前提のため不要。実行はティラノスクリプトが担う
- CLI・出力系（main.rs / report.rs 約1,000行）: 上記に付随するため不要

## tsumugaiをアーカイブする理由

- 解決したかった問題（書式入力によるシナリオ思考の中断、シナリオの検証可能性）が、`voice-to-tyrano`＋ティラノスクリプトの構成でより単純に実現できると判断したため
- 独自記法・独自ランタイムを保守し続ける理由がなくなったため
- 再利用可能な設計知識は本文書および本リポジトリの各文書へ移行済みのため
