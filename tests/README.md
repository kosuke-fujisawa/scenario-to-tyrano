# tests/README.md

将来的なテスト観点の整理。現時点でテストコード・検査スクリプトは実装しない（AGENTS.md参照）。Skillの改善は`examples/`の入力と期待出力の差分をもとに行い、コード化の必要性が確認できた段階で、ここに挙げた観点を静的検査へ移す。

## 変換品質

Skillの変換結果が満たすべき性質。

- 原文のセリフが保持される（推敲・言い換えがない）
- 原文の地の文が保持される
- 原文にない内容（演出・分岐・設定）が追加されない
- 原文の `[` / `\` / 行頭制御文字が、ティラノ構文に誤解釈されず本文として保持される
- 話者が正しく解釈される
- 入力由来の不要な改行に影響されない（改行位置ではなく意味で判断する）
- 明示的な「改ページ」の意図が`[p]`として反映される
- 明示的な「少し間」の意図が`[wait]`として反映される
- 選択肢が正しく生成される（`[glink]`の列挙と`[s]`）
- 状態変化が正しく生成される（数値は入力で明示されたもののみ）
- 遷移先が正しく生成される

## 入力表現の違い

同じシナリオ意図が異なる表現で入力された場合の変換品質。本Skillは入力形式を固定しないため、次の違いに対して結果が大きく損なわれないことを検討対象とする。

- 音声文字起こし風の入力（句読点・改行が不正確、編集指示の言葉を含む）
- 通常の文章
- 脚本形式（`名前「セリフ」`など）
- 箇条書き・構成メモ
- 改行が少ない文章
- 改行が多い文章

初期版でこれらすべてを自動テストする必要はない。設計上のテスト観点として記録し、将来の追加例（`spoken-transcript`、`screenplay`、`bullet-notes`など）の候補とする。

## 構造検査

生成された`.ks`が満たすべき構造的性質。tsumugaiのcheck（静的検査）/ routes（到達可能性検査）の検査観点を引き継いだもの。

静的検査（`.ks`単体・プロジェクト横断で確認できるもの）:

- ラベル重複（同名ラベルが同一ファイルに複数ない）
- 未定義ジャンプ先（`[jump]`/`[glink]`の`target`が存在するラベル・ファイルを指す）
- 分岐の閉じ忘れ（`[if]`に対応する`[endif]`がある。選択肢の後に`[s]`がある）
- 存在しない素材参照（`storage`指定のファイルがプロジェクトに実在する）
- 未定義変数（`[if]`等で参照する変数が事前に代入されている）
- 未初期化変数への加算（初期値を確認できない状態変化は実行可能なタグにしない）
- 未解決TODO（`; TODO(author):`コメントの残数を把握できる）

到達可能性検査（経路をたどって初めて分かるもの。tsumugaiではcheckとroutesを責務分離していた）:

- 到達不能ラベル（どこからも遷移されないラベル）
- 意図しないフォールスルー（分岐後の合流・停止漏れで次のラベルへ流れ込む）

## 回帰確認

`examples/*/input.txt`を入力し、生成結果が`expected.ks`の意図から逸脱していないことを確認する。

**未決の設計論点**: 完全一致を必須にするか、意味的な一致を評価するかは現時点で決め切らない。

- 完全一致（ゴールデンテスト。tsumugaiではこの方式を採用していた）: 判定が決定的で回帰検出が確実。ただしLLMによる変換は表記揺れ（ラベル名、コメント文言、タグの属性順）が避けにくく、偽陽性が多くなる恐れがある
- 意味的な一致: セリフ・地の文の保持、ラベル構造・遷移グラフの同型性など、性質単位で評価する。揺れに強いが、評価器の実装・維持が必要

初期版では、`expected.ks`を「期待される変換の例」として扱い、人間が差分を見て判断する。
